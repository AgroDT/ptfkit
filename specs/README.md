# PTF Specifications

Each standalone YAML file in `functions/` describes one scientific source. Its
format is defined by [`schema/ptf-spec.schema.json`](./schema/ptf-spec.schema.json).
The `scientific_notes` field retains formulas, derivations, numerical policy,
golden cases, and scientific decisions.

The JSON Schema and `cargo run -p ptfkit-codegen -- validate` are the format and
semantic contracts. `ptf-extract` writes a blocked or review-ready draft;
`ptf-generate` alone marks a source implemented after generated targets pass.

## Package-wide contracts

Unless a future specification explicitly documents a justified exception, the
public Python layer is keyword-only, accepts scalars and NumPy arrays, follows
NumPy broadcasting, supports `out`, and uses `f64` Rust kernels. These
package-wide contracts must not be repeated in individual source specifications.

Each specification filename stem is an APA-style source slug and defines exactly
one public Python module: `ptfkit.<apa_article_key>`. It is generated by
default, so omit `generation`. Set
`generation.public_python: manual` only for an intentional manual module; its
wrapper continues to use generated native ufuncs rather than duplicating PTF
formulas.

Its `source` metadata contains the module summary (at most 100 characters),
the complete APA citation, and either `null` or a DOI identifier plus its URL.
The generator uses these values verbatim rather than deriving a summary or DOI
link.

Function front matter records source-specific public API, ordered inputs and
outputs, golden cases, edge cases, scope, and short documentation notes. For a
single output,
`result_class` is `null`; multiple outputs use the documented result class.

Top-level `scope.territory` describes the complete territory of the source and
its public module. A function may independently declare `scope.territory` only
when its territory is narrower or different. Function territory never inherits
or overrides the module territory.
